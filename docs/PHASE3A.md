# Phase 3A：iPhone 日光习惯记录 MVP

## 数据规则

- `DaylightSession` 保存 UUID、绝对开始/结束时间和 `.manual` 来源，遵循 Codable、Sendable、Equatable、Identifiable。
- 时长由 `end - start` 推导，避免持久化另一份可能不一致的时长。JSON 使用 Foundation Codable 的 Date 默认编码，schema version 为 1。
- 起止时间必须有限且位于 Foundation `distantPast...distantFuture`，结束必须严格晚于开始。零时长、负时长、NaN、无穷大及超范围日期均拒绝，解码也执行同样校验。
- Journal 拒绝重复 ID、重叠记录、重复开始及重复结束；相邻记录允许。手动补记不得晚于当前时间，也不能和正在计时的活动重叠。
- UI 目标范围为 1～1440 分钟，默认 30。共享汇总对零/负目标仍沿用 DaylightProgress 的归零规则。
- 目标是当前全局设置，修改后所有历史比例重新计算，不保留每个历史日的旧目标。

## 自然日与精度

使用调用时的 `Calendar.current` 及其时区，通过 `dateInterval(of: .day, for:)` 得到自然日边界。
每条记录与该日的半开区间 `[start, end)` 求交，不假定一天固定 86400 秒。
跨午夜记录的详情保留完整起止时间，同时显示当天分段；恰在午夜结束不会重复计入次日。
更换时区后按新时区重新归日，存储的绝对时间保持不变。

每日精确秒数先汇总，再一次性向下取完整分钟，交给现有 DaylightProgress 计算进度和剩余分钟。
例如两条各 30 秒的记录合计 1 分钟。UI 显示秒数，但进度不是逐秒变化；计入不足 1 分钟时进度仍为零。
汇总保护浮点相加和秒转 Int 的上界；相同 ID 在独立汇总 API 中只计一次。
独立汇总 API 会累计不同 ID 的时长；正常 Journal 入口会预先拒绝时间重叠。

## 计时和文件存储

计时以持久化的开始时间与当前 `Date()` 的差值计算，TimelineView 只负责刷新，不累计触发次数。
恢复前台会刷新参考时间；进入后台不申请持续计时权限，也不要求后台执行 Timer。
正在计时期间的今日累计包含临时计算的当日分段，历史页只显示已完成并保存的 Session。
忘记结束会持续计时至下一次手动结束；不自动推断活动结束。

`@MainActor DaylightStore` 管理 UI 状态，`DaylightJournalFileStore` actor 串行执行文件 I/O。
文件位于 App 的 `Application Support/DaylightApp/journal-v1.json`，不使用缓存目录。
每次保存整个 Codable 快照，通过 `Data.write(options: .atomic)` 替换目标文件。

- 开始：先保存含 stable ID 和开始时间的快照，成功后显示正在计时。
- 结束：生成同一 ID 的 Session，原子保存记录和清除 active 状态，成功后才更新 UI。
- 保存进行中禁用相关操作，MainActor 内还有重复操作保护。
- 写入失败：保持之前成功保存的状态，明确显示错误；结束失败时计时继续，下一次重试使用新的结束时刻。
- 读取失败：不把损坏、权限或未知版本错误当作空数据，阻止继续写入，可重试读取。不会自动删除损坏文件。
- 仅文件不存在时以新 Journal 启动。尚未提供导出、备份恢复或自动修复界面。

自然时区变化不改变经过时长。若用户手动调整系统时钟，Date 差值也会受影响；
时钟早于开始时显示警告并将显示时长限制为零，拒绝结束为零/负时长记录，保留原计时供校正后重试。
没有引入跨重启的单调时钟校正机制。
